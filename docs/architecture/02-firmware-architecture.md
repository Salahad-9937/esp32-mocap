# 2. Архитектура встраиваемой прошивки ESP32 {#sec-firmware-architecture}

## 2.1. Модульная организация каталога firmware

Прошивка микроконтроллера разрабатывается на языке C++ с использованием нативного фреймворка ESP-IDF / Arduino Core без применения сторонних высокоуровневых библиотек датчиков. 

Каталог `firmware/` структурирован на независимые функциональные модули:

```text
firmware/
├── esp32-mocap.ino         ── Главная стейт-машина (Setup, циклический поллинг Loop)
├── config.h                ── Константы: пины SDA/SCL, тайминги, дефолтные адреса
├── i2c_bus.h / .cpp        ── Низкоуровневые транзакции Wire, таймауты и сброс зависшей шины
├── bus_scanner.h / .cpp    ── Автоматический поиск активных MUX (0x70..0x77) и узлов BMI160
├── sensor_driver.h / .cpp  ── Прямая регистровая инициализация BMI160 и пакетная выборка
├── packet_builder.h / .cpp ── Сборка бинарного фрейма, инкремент счетчика и расчет CRC-16
└── bt_transport.h / .cpp   ── Инициализация Bluetooth SPP и потоковая передача кадров
```

## 2.2. Низкоуровневый драйвер шины и восстановление зависаний (Bus Recovery)

Шина I2C в носимых системах с длинными кабелями подвержена паразитным помехам: если ведомый датчик зависает в момент удержания линии SDA в низком логическом уровне (ACK state), стандартные библиотечные вызовы намертво блокируют микроконтроллер.

### Архитектура модуля `i2c_bus`:
* **Аппаратный сторожевой таймер транзакций (I2C Timeout):** Каждая операция чтения и записи ограничивается предельным аппаратным таймаутом в $1.5$ мс. При превышении лимита операция принудительно прерывается с кодом ошибки.
* **Активация сторожевого таймера датчика (I2C Watchdog в BMI160):** В регистре `0x70` (`NV_CONF`) бит `i2c_wdt_en` устанавливается в `1`, а период `i2c_wdt_sel` — в 50 мс. При залипании шины кристалл BMI160 аппаратно сбрасывает собственный I2C-интерфейс.
* **Процедура сброса зависшей шины (Bus Clear / Clock Pulsing):**
  * Если при инициализации или в процессе работы линия SDA остается прижатой к земле, микроконтроллер временно переводит вывод SCL в режим дискретного GPIO-выхода.
  * Генерируется серия из 9 импульсов тактового сигнала SCL с частотой $\sim 100$ кГц. Это принуждает зависший ведомый узел завершить передачу бита и отпустить линию SDA.
  * Формируется корректная I2C-стоповая последовательность (Stop Condition), после чего аппаратный контроллер I2C реинициализируется на рабочей частоте 400 кГц.

## 2.3. Алгоритм динамического автосканирования дерева шины (`bus_scanner`)

Модуль сканирования устраняет необходимость хардкода количества и адресов подключенного оборудования:

* **Структура активного узла (`ActiveNode`):**
  * Компактная структура, содержащая 8-битный I2C-адрес мультиплексора (`mux_addr`) и номер канала (`channel` от 0 до 7).
* **Статический пул топологии:** Предвыделенный плоский массив емкостью до 64 элементов `ActiveNode` и счетчик фактически обнаруженных узлов $N_{active}$.
* **Двухфазный алгоритм сканирования при старте:**
  1. *Фаза сканирования коммутаторов:* Опрос адресного пространства от `0x70` до `0x77`. При получении ответа `ACK` адрес заносится во временный список обнаруженных мультиплексоров.
  2. *Фаза зондирования каналов:* Для каждого найденного мультиплексора поочередно активируется маска каналов $(1 \ll C)$. На активную шину отправляется запрос чтения регистра `0x00` (`CHIP_ID`) по адресу `0x68`. Если датчик ответил эталонным кодом `0xD1`, комбинация `[Адрес Мультиплексора, Канал]` регистрируется в основном рабочем пуле.

## 2.4. Прямой регистровый драйвер датчика (`sensor_driver`)

Модуль взаимодействует с микросхемой BMI160 напрямую через аппаратные регистры с соблюдением обязательных пауз переключения режимов питания из официального даташита:

* **Регламент инициализации узла:**
  1. *Программный сброс (Soft Reset):* Запись команды `0xB6` в регистр `0x7E` (`CMD`). Пауза $100$ мс на перезагрузку цифрового ядра и загрузку калибровочных констант из NVM.
  2. *Проверка идентификатора кристалла:* Считывание регистра `0x00` (`CHIP_ID`). Подтверждение кода `0xD1`.
  3. *Включение акселерометра в Normal Mode:* Запись команды `0x11` в регистр `0x7E` (`CMD`). Пауза не менее $5$ мс (согласно Таблице 24 даташита, типичное время перехода составляет $3.2$ мс, максимальное — $3.8$ мс).
  4. *Включение гироскопа в Normal Mode:* Запись команды `0x15` в регистр `0x7E` (`CMD`). Пауза не менее **$80$ мс** (согласно Таблице 24 даташита, типичное время выхода резонатора на стабильный режим составляет $55$ мс, предельное — $80$ мс).
  5. *Проверка статуса питания (PMU_STATUS):* Чтение регистра `0x03`. Подтверждение битовой маски `0x14` (биты 5:4 = `01`b, биты 3:2 = `01`b).
  6. *Конфигурация диапазонов:*
     * Запись значения `0x05` в регистр `0x41` (`ACC_RANGE`) $\rightarrow$ шкала $\pm 4g$ (чувствительность $8192$ LSB/g).
     * Запись значения `0x02` в регистр `0x43` (`GYR_RANGE`) $\rightarrow$ шкала $\pm 1000^\circ/\text{с}$ (чувствительность $32.8$ LSB/(°/s)).
  7. *Конфигурация выходной частоты данных (ODR):*
     * Запись значения `0x28` в регистр `0x40` (`ACC_CONF`) $\rightarrow$ фильтр нормального режима, ODR = 100 Гц.
     * Запись значения `0x28` в регистр `0x42` (`GYR_CONF`) $\rightarrow$ фильтр нормального режима, ODR = 100 Гц.
* **Пакетное считывание вектора измерений:**
  * Отправка начального адреса `0x0C` (`DATA_8`) без генерации Stop-условия (Repeated Start).
  * Прямой прием 12 байт в предварительно выделенный целевой срез буфера кадра.
  * Структура принятого массива: байты 0..5 соответствуют гироскопу ($Gx, Gy, Gz$), байты 6..11 соответствуют акселерометру ($Ax, Ay, Az$).

## 2.5. Конструктор кадра и Bluetooth-транслятор

* **Структура формируемого кадра:**
  * Преамбула синхронизации: 2 байта (`0xAA`, `0x55`).
  * Порядковый номер пакета: 2 байта (`uint16_t`, инкрементируется с переполнением).
  * Количество переданных датчиков: 1 байт (`uint8_t`, значение $N_{active}$).
  * Полезная нагрузка: $N_{active} \times 12$ байт сырых целочисленных значений (порядок следования: $Gx, Gy, Gz, Ax, Ay, Az$).
  * Контрольная сумма CRC-16 (полином `0x1021`, начальное значение `0xFFFF`): 2 байта, вычисляемые по всему содержимому кадра, исключая преамбулу.
* **Модуль Bluetooth SPP (`bt_transport`):**
  * Инициализация стандартного стека Bluetooth Classic под именем устройства `ESP32_MOCAP_HUB`.
  * Передача сформированного кадра единым вызовом `BluetoothSerial::write(buffer, length)`.
  * Запрет на использование строкового форматирования, текстовых логов и промежуточных строковых буферов во время активной трансляции.

## 2.6. Политика управления памятью и главный цикл

* **Zero Dynamic Allocation:** В коде прошивки полностью запрещено использование динамического выделения памяти на куче (`malloc`, `free`, `new`, `delete`, контейнеров `std::vector`, `String`). Все буферы кадров, массивы топологии и дескрипторы имеют фиксированный размер времени компиляции.
* **Стейт-машина главного цикла:**
  * Состояние `INIT`: восстановление шины, автосканирование топологии, инициализация датчиков с выдержкой аппаратных пауз, запуск Bluetooth-сервера.
  * Состояние `WAIT_CONNECTION`: ожидание подключения клиентского устройства (ПК) по Bluetooth.
  * Состояние `STREAMING`: циклический опрос активных датчиков с шагом времени, синхронизированным с аппаратным таймером микроконтроллера, сборка и немедленная отправка кадра.
  * Состояние `ERROR_RECOVERY`: попытка сброса шины I2C импульсами тактовой линии при фатальном сбое обмена.
